Ustaad: three phones, one local AI cluster

The models worth running do not fit on one phone, and the files worth asking about should not leave it.

An Android app that joins two or three phones on one Wi-Fi into one cluster: a scheduler that gives each job to the best free phone, a signed idempotent protocol between phones, failover when one stops answering, and a model too big for any one phone split by layer range across all three. No cloud model in the loop.

Built solo in 48 hours for the iQOO Hackathon 2026 Grand Finale in Bengaluru and run on three iQOO 15 phones. Each phone runs llama.cpp model servers as child processes; the phones share jobs, questions about their own files and memory over HTTP, every request and every reply signed. Nothing in the protocol is tied to one phone model: any device that runs llama.cpp and speaks the same signed HTTP protocol can join, and the scheduler already places work by each device's measured speed.

Secure by design. Every request and every reply is signed with HMAC-SHA256 and refused after 30 s. A wrong secret, a stale clock or a tampered answer card is rejected. A phone joins only after the owner confirms the pairing, private folders never leave the phone, and the endpoint for other apps is closed to the network and needs the owner's key. Traffic is signed, not encrypted.

On top of that link: the phones answer the same problem and revise where they disagree, each phone searches its own files and sends back only short snippets, never the files, and answers are shared as signed cards. Other apps on the phone reach the cluster through an OpenAI-format endpoint. A model that will not fit is refused in 0.4 s instead of 134 s of swap thrashing. Every figure below is one run on a debug build unless it says otherwise.

  • 2.57xthe throughput of the fastest single phone: 30.91 tok/s across three phones against 12.03, on a batch of 32 short prompts on the GPU, mean of five runs (2.40 to 2.65).
  • 18.6 GBmodel that one phone cannot run (no token in 134 s) runs across three phones, split by layer range with one range per phone: 5.7 to 6.4 tok/s, first token 1.5 to 2.8 s. One run.
  • 80%faster second load of that split, 319 s to 65 s, with the weights cached on the two lending phones.
  • 700 of 700requests completed through path failovers, none lost, none run twice: an idempotent id on every request that changes state, so a resend runs once. Paths were cut with a fault hook, not by switching Wi-Fi off.
  • 2.3 sto drop a phone force-stopped in the middle of a batch; 32 of 32 jobs still finished. If the coordinating phone dies, the batch ends.
  • 1,594unit tests, 0 failures. 727 commits in six days, solo. Gates closed only on numbers measured on real phones; a final audit by four independent readers, 52 findings fixed with unit tests.
